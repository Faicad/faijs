# Agent Note: faijs-viewer package for third-party `.fai.zip` viewing

Status: implemented

English | [中文](2026-10-03-fai-zip-viewer-sdk-implemented.zh.md)

## Problem

Any third party wanting to render a project `.fai.zip` 3D document had to know how
to read the container, assemble an execution host environment, plug in the occt /
manifold / brepkit wasm engines, and turn execution results into mesh data. There
was no single package a consumer could depend on.

## Decision

Ship a new independent workspace package `@faicad/faijs-viewer` that owns the whole
viewing chain. A third party depends on exactly one package and calls the v1 entry:

```ts ignore-check
openFaiZip(bytes, { wasm: { occtUrl, manifoldUrl, brepkitUrl } })
```

- `wasm` is **required** and all **three urls must be non-empty strings**. A
  missing or empty url is a caller contract violation and **throws** `E_WASM_URL`;
  it is not a per-bytes render failure.
- Container errors, execution failures, and "no visible geometry" return
  `result.error` with `code ∈ { E_CONTAINER, E_EXECUTION, E_NO_GEOMETRY }`.
- In a browser the three urls bind the occt/manifold engines; in a Node runner
  they are validated but local wasm auto-loads, so tests execute real geometry.
- The container is read with `@faicad/faijs/io/fai-zip`; the active (or requested)
  model's source is executed via `createRuntime` bound to browser ports (asset
  resolver + container module loader); visible terminal shapes (`TerminalShape`),
  filtered of `hidden`, are returned as structured `FaiViewerMesh` arrays.
- No runtime dependency on `@faicad/faijs-extra` / `sheetmetal`; the only runtime
  dependency is `@faicad/faijs` (peer), plus `occt-wasm` (peer, lazily imported
  only for browser `OcctKernel` init).
- v1 does **not** bundle wasm assets; the README gives the self-hosting recipe for
  the three wasm files.
- The existing occt-import-js kernel stays in the viewer products; the two kernels
  coexist rather than merge (per the plan decision).

## Alternatives considered

- Reuse the existing occt-import-js CAD→GLB path: rejected — `.fai.zip` has no
  baked mesh; it must execute faijs scripts, and the SDK must stay kernel-agnostic
  for third parties.
- Fold the viewing chain back into `@faicad/faijs` core: rejected — the user chose
  an independent package so a third party depends on exactly one viewer package
  and need not assemble host/worker/engines.
- Make brepkit the mesh-boolean backend and drop manifold: rejected — brepkit's
  mesh-boolean is not wired into the boolean slot in v1, so `manifoldUrl` stays a
  required (validated-but-unconsumed) field.
- Ballot in core via auto-host assembly: rejected — a caller-facing `wasm` object
  is simpler in v1; future zero-config preset is out of scope.

## Engineering notes

- No pre-baked mesh in `.fai.zip`: rendering executes model scripts at runtime.
- A GOTCHA surfaced while writing tests: an entry that `import`s an absent module
  does **not** fail — the runtime tolerates it and still produces a mesh. To make a
  model deterministically fail in a regression test, force a script-level throw.
- The viewer validates the three urls even in Node before running; consuming
  fixtures that pass only validated (un-reachable) urls still produce real meshes.

## Acceptance criteria

- [x] `openFaiZip` returns non-empty `meshes` for a minimal `cad.box` container.
- [x] Empty `occtUrl` throws `E_WASM_URL`; invalid bytes -> `{ error }` `E_CONTAINER`;
  a throwing model -> `{ error }` `E_EXECUTION`.
- [x] `@faicad/faijs-viewer` type-checks, passes its vitest, builds to `dist/`, and
  passes `check-ghost-deps`, `check-lockstep`, `check-workspaces-order` with the
  CDN `versions.json` regenerated by `gen-importmap`.
- [x] Opens real `fcstd-port/**/*.fai.zip` samples in Node: several render meshes;
  some models report genuine per-part deviations as `E_EXECUTION`.

## Consequences (user-chosen v1 extension: real FreeCAD sketch/draw support)

The user chose to extend v1 so `openFaiZip` can execute **real FreeCAD-converted
containers** that call `cad.sketch` / `cad.draw`, not just pure core ops like
`cad.box`. `openFaiZip` now:

- merges the sketch + draw namespaces **into the `cad` binding** it registers:
  `runtime.registerLib('cad', mergeDrawNamespace(mergeSketchNamespace(createApiNamespace())), { default: true })`
  after `registerSketchSymbols()` + `registerDrawSymbols()`;
- installs the planegcs constraint solver via `installSketchSolver`. In a **Node**
  runner it auto-loads `@faicad/faijs-sketch/node` -> `createNodePlanegcsSolver`
  (the quickly `node:` import stays dynamic so the browser bundle never pulls a
  `node:*` module). A browser host self-hosts `planegcs.wasm` and passes
  `opts.sketch.planegcsUrl`; without it, sketch ops surface `E_SKETCHC_NO_SOLVER`
  through `OpenFaiZipResult.error`.
- declares `@faicad/faijs-sketch` + `@faicad/faijs-draw` as **peers** alongside
  `@faicad/faijs` (the "one package" contract is preserved: the host provides all
  three family packages). The electron consumer file-links them.

Verified: `openFaiZip` renders a synthetic `cad.sketch{rect}+extrude` container
(5/5 viewer tests pass); the electron's real `loadFormat('fai')` path now opens
the fcstd-port `Group01.fai.zip` (People symbols) and renders it. The prior
`cad.sketch is not a function` failure is gone.

**Unresolved (recorded honestly):** two real library samples — `ThreePartRight`
and `Double glass sliding doors...` — still fail, with
`E_SKETCHC_NO_GEOMS: sketch requires at least one geometry`. Decompiling the
converted `main.fai.js` shows the converter emits `cad.sketch({ contours: [...] })`,
but the sketch op's input contract accepts only `shapes` / `geoms`; `contours` is
an output concept, not an input. This is a **converter ↔ sketch contract mismatch
in the faijs family, not a viewer wiring bug**; it needs either the sketch op to
alias `contours` (a design decision in `@faicad/faijs-sketch`) or the fcstd-port
converter to emit `shapes`/`geoms`.
