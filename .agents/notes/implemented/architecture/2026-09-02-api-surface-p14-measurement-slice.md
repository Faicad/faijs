# Agent Note: API surface completion — P14 first slice (measurement module full projection, multi-module generator)

Status: implemented

English | [中文](2026-09-02-api-surface-p14-measurement-slice.zh.md)

## Problem

P13 proved the E5 generation mechanism on a 4-symbol sample slice, but the projection pipeline was single-module (`generate()` hard-coded `topology`), the query template only supported one geometry `Shape` argument, and no full module had been projected. P14's job is to expand the mechanism area by area: multi-module artifacts, a positional query template (multi-`Shape` / `Shape[]` / numeric passthrough), and a first fully-projected module as the pattern for every later batch (`operations`, `core`, `sketching`, `2d`, `io`, `gear`, `query`, `projection`, `text`).

## Decision

- **The generator is now multi-module.** `scripts/gen-l3-surface.ts` exposes a pure `generateModule(module)` (shared by CLI `main()` and the test) plus the backward-compatible `generate()` == `topology`. `PROJECTED_MODULES` drives `output/generated/<module>.ts` writes; each module is a slice of `ARG_SPEC` selected by an entry's `module` field (default `topology`, P13-compatible).
- **The query template generalizes to positional arguments.** A query entry declares `queryParams` (faijs-facing name + type + optional + docs) and `geometryArgs` / `geometryCollectionArgs` (which positional indices are single faijs `Shape`s vs `Shape[]` arrays to be borrowed into brepjs handles). Non-geometry params (numbers, options) pass through untouched. The generated faijs signature mirrors the brepjs positions, and the caller-facing return type is annotated explicitly (`returnType`) to satisfy the export-JSDoc gate's `@param`/`@returns` requirement.
- **First full-module slice = `measurement`** (21 unexcluded symbols, all data queries + types, no brep-op). `generated/measurement.ts` projects 8 type re-exports (`CurvatureResult`, `DistanceProps`, `InterferencePair`, `InterferenceResult`, `LinearProps`, `PhysicalProps`, `SurfaceProps`, `VolumeProps`) and 12 queries (`measure*`, `checkInterference`, `checkAllInterferences`), whose result `Result`s are unwrapped (err → throw) and whose array input (`checkAllInterferences`) is element-borrowed.
- **A follow-up batch adds the small pure modules `text` (5 projected: `fontMetrics`, `getFont`, `textMetrics` + 2 metric types; 3 skips) and `projection` (4 pure camera/plane funcs + 3 types; 2 skips).** These exercise the `pure` (value) and `type` projection paths at zero extra machinery — no brep-op, no query. The skips record the pattern for functions a static faijs function cannot faithfully model: `loadFont` (fetch + global registry side effects — host font source needed), `sketchText`/`textBlueprints` (return brep-side DSL objects over a loaded-font registry), and `projectEdges`/`makeProjectedEdges` (return cloned-`Edge[]`-handle arrays with per-result compound ownership — a multiple-product adoption model faijs does not yet have). Each skip carries a `reason` so the divergence is reviewable, not silent. Progress: text 5 + 3 skip (=8 unexcluded), projection 7 + 2 skip (=9 unexcluded) — both modules fully accounted against `upstream-surface.json`.
- **A third batch covers the `query` module** (14 symbols: 8 type re-exports + 6 skips). The finder family (`edgeFinder`/`faceFinder`/`wireFinder`/`vertexFinder`/`cornerFinder`, `getSingleFace`) is a stateful chained-builder tool in the same category as `createDistanceQuery`: each factory returns a `ShapeFinder` DSL object holding closure state, so a static faijs function cannot faithfully model the lifecycle — all six values register `skip` + `reason`. The 8 type exports (`EdgeFinderFn`, `FaceFinderFn`, `ShapeFinder`, `SingleFace`, `CornerFilter`, …) are re-exported: they are reusable query-contract type shapes with no runtime semantics of their own.
- **A fourth batch covers the `ns` module** (9 symbols, all `pure`). These are namespace objects: the vendored root barrel aggregates each submodule with `export * as booleans from './ns/booleans.js'`, so the surface record's `file` (`./ns/booleans.js`) names the submodule while the real export value lives on the root barrel. The adapter therefore points `source` at the root barrel (`index.js#booleans`), and the emitted line re-exports the whole namespace object (`export { booleans } from …/index.js`) rather than flattening its members. This keeps brepjs's organization shape (pure-family user code reaches `booleans.fuse(…)` untouched) at no adapter machinery — the `pure` template already handled plain re-export, only the `source` target differs. Progress: ns 9 = 9 unexcluded, fully accounted.
- **A fifth batch covers the `gear` module** (17 symbols: 11 type re-exports + 3 `pure` + 3 skips). The pure members are the math/validator helpers (`gearGeometry`, `planetPlacements`, `validatePlanetary`) — no Shape parameters, so they pass straight through. The three `make*Gear` constructors are skipped with reason, extending the composite-result category: each returns a `Result` wrapping multiple BREP handles (`GearResult` = a solid plus measured diameters; `PlanetaryGearAssembly` = sun + planets[] + ring), which the current op templates cannot carry — `brep-op` adopts a single product and `query` returns a scalar/array, so a multi-handle object result needs the host-side adoption model (the same gap behind the `projectEdges` skip). Their type surfaces still project, so gear results can be typed in faijs today; constructing gears is deferred to the E12 wiring point. Progress: gear 14 + 3 skip = 17 unexcluded, fully accounted.
- **A seventh batch covers the `io` module** (28 symbols: 12 type re-exports + 16 skips). The `export*`/`import*` family is **not** directly projected — file/byte exchange belongs to the faijs `node-host` / `browser-host` port adapters (the IO decision adopted in P14), not to a static pass-through; several also consume non-faijs inputs (`exportOBJ` takes a `ShapeMesh`, `exportDXF` takes `DXFEntity[]`) and `importSVG`/`importSVGPathD` return a kernel-handle `Blueprint` (the 2d family). All 16 values register `skip` + reason pointing at the host-ports route. The 12 types (`DXFEntity`, `DXFExportOptions`, `DXFImportOptions`, `GltfExportOptions`, `GltfFace`, `GltfMaterial`, `MaterialFn`, `StepExportOptions`, `StepExportPart`, `SVGImportOptions`, `ThreeMFExportOptions`, `ThreeMFMaterial`) re-export so faijs can type-check host-port data today. Progress: io 12 + 16 skip = 28 unexcluded, fully accounted.
- **A sixth batch covers the `2d` module** (45 symbols: 12 type re-exports + 33 skips). The `2d` module is the whole "2D sketchbook" subsystem: value factory/transform/boolean helpers consume or return kernel-handle-wrapped objects (Curve2D, Blueprint, Blueprints) in an interlocked DSL with registerForCleanup-decorated lifespans. These are not faijs Shapes and match neither the single-product brep-op template nor the scalar query template; naive re-exports would leak kernel handle objects with their own dispose onto the faijs face. Values register skip with reason, pending host-side 2D integration (E12) that carries the lifecycle; the 12 types (Blueprint, Blueprints, CompoundBlueprint, Curve2D, DrawingInterface, GenericSketcher, Point2D, BoundingBox, ScaleMode, Shape2D, SketchData, SplineOptions) re-export unchanged for typing host-provided 2D data today. Progress: 2d 12 + 33 skip = 45 unexcluded, fully accounted.
- **One skip registered**: `createDistanceQuery` is declared `skip` + reason in arg-spec — it returns a stateful closure (`distanceTo`/`dispose`) that a static faijs function cannot model (needs a host adapter, not a pass-through projection).
- **The adaptation table remains the single manual list.** No hand-written wrappers; every emitted line derives from `ARG_SPEC` (now prototyped for all modules). The sync guard in the extended `surface-mechanism.test.ts` iterates `PROJECTED_MODULES` and asserts `generateModule(m) ===` the committed `generated/<module>.ts` (drift fails), and each entry's emission shape matches its kind.
- **Independence remains.** The new slice is **not** re-exported from `api/index.ts` / `api-namespace.ts` — wiring the export face is the P14/E12 terminal state; exposing it early would break the U7 key-set equality assertion (C).

## Alternatives considered

- **Project `operations` first (the plan's nominal first batch).** Rejected for the first slice: `operations` is the largest and mixes geometry ops, joints/history/assembly/IO semantics whose classification needs deferred arbitration per §5.2; `measurement` is a small, homogeneous, pure-query module — the right pilot to generalize the mechanism safely before the big modules.
- **Keep `generate()` single-module, add `operations.ts` as the first artifact.** Rejected: the query position generalization (multi-`Shape`, arrays, numeric passthrough) is what the later batches need; validating it on `measurement` (which exercises both single- and double-`Shape` queries plus an array query) proves the template before the heavy modules.
- **Put the skip (`createDistanceQuery`) into `upstream-exclusions.json`.** Rejected: it is not an upstream exclusion, it is a declared divergence in the projection layer; keeping it as `ARG_SPEC` kind `skip` with `reason` keeps it visible in the adapter table and reviewable with the rest of the batch.
- **Add a runtime (OCCT-wasm) suite for measurement now.** Deferred exactly as in P13: runtime execution needs the full host wiring, which lands with the later P14 wiring point; the structural/sync gate is the contract for each batch, with runtime coverage accompanying that wiring.

## Consequences

- `generated/measurement.ts` compiles, passes the repo `export-jsdoc` run (+0 violations: templates emit explicit `@param`/`@returns`), the U8 branding guard is happy, and the full core suite (933 tests) is green; the gate's pre-existing 91-violation baseline (chiefly `packages/sheetmetal` JSDoc debt) is unchanged and orthogonal.
- The first complete module demonstrates the slice discipline the remaining batches follow: pure-query/type modules need no brep-op-specific work; mixed modules (e.g. `operations`, `io`) reuse the same positional machinery plus their per-module arbitration (§5.2).
- Progress is tracked in the plan (`P14` first-slice mark).
