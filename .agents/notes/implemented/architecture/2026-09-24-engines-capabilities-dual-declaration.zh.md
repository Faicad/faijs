# Agent Note：engines 与 capabilities 是两条独立声明轴

Status: implemented

[English](2026-09-24-engines-capabilities-dual-declaration.md) | 中文

## Problem

`defineOp` 上有两个声明字段。`engines` 表达平台身份——本实现能跑在哪些引擎上；`capabilities`
表达本实现所需的内核能力。`assertLibConforms` 里有一条装配期断言：任何同时声明两者的 op
一律拒绝，给出的理由是「平台 op 的能力由平台自己保证，且能力名空间只收 L1 中立名」。

这个理由与事实不符。`BrepCapabilityName` 包含 `BrepMethodKind`——一串**逐核方法真名**
（`isNull`、`dispose`、`chamfer`、`shell`、`loft` …），它是内核名空间，不是 L1 中立名空间。
平台 op 声明一个内核方法名并不越界。

两个字段回答的是正交的两个问题：`engines` 收窄「跑在哪些引擎上」，`capabilities` 说明
「需要哪些内核方法」。平台 op 对两个问题都有答案，且答案不冲突。

互斥让作者被迫丢弃真实信息。compat op `fuse` 依赖 `kernel.isNull` 与 `kernel.dispose`；
在两个轴之间二选一时，它的声明留下了 `engines: ['occt']`，丢掉了依赖清单——并在同一个对象
字面量旁边留下了一段注释，论证两个字段互为补充，而对象里只剩其中一个。能力覆盖守卫也因此
只能写成两个互斥集合相加的形式，因为一个条目永远不可能同时被两个轴计入。

它还移走了一道可用的静态防线。只靠中立轴声明能力的 op，可能被一个「族级能力位过度声明」的
引擎（族级布尔覆盖了该引擎实际并未实现的方法）放行，通过静态判定后在核内失败——甚至更坏，
静默返回错几何。这正是本项目静态分派红线要禁止的形态。

## Decision

两个字段互相独立，可以同时声明。

- `engines` 是引擎白名单：op 只在列出的引擎上运行。它被最先判定，先于任何能力或模式考虑。
- `capabilities` 是实现的内核依赖清单。它在引擎匹配之后，与该引擎的声明求交。
- 同时声明意味着「只在这些引擎上，且要求这些能力」。目标引擎缺少所声明的能力时仍然静态
  失败、且失败发生在实现体执行之前——这个组合永远不会静默放行。
- `assertLibConforms` 不再拒绝这个组合。声明形状仍然校验：`capabilities` 必须是字符串数组，
  `engines` 必须是非空的已知引擎 id 数组。

## Alternatives considered

- **保留互斥。** 否决：其给出的理由不成立，且强迫作者丢弃真实的依赖清单——与能力表赖以
  建立的「诚实声明」原则正好相反。
- **让 `engines` 一票定音——一旦声明了 `engines`，`capabilities` 仅作说明性记录。** 否决：
  这等于丢掉一道静态防线。声明了目标引擎所缺能力的 op 会被门放行、再在核内失败，正是静态
  分派规则要防的运行时失败形态。求交则在声明诚实时零成本，同时让每一条被声明的需求都可执行。
- **扩充逐核方法表，让中立轴也能表达同样意图。** 不选：那是大得多的改动（方法名联合 + 两个
  引擎的声明表），而且回答的是另一个问题。声明轴不应该靠扩充词表来绕开；让两条轴可组合，
  修的才是真正的缺陷。

## Consequences

- 平台 op 可以一次性说清身份与依赖。实现确实需要具名内核方法的 op 不必再藏起两个事实之一。
- 门控次序可观测、且已被测试钉住：非目标引擎下引擎门触发（文案点名引擎、不含能力名）；
  目标引擎下能力门触发（文案点名能力名）。两种情况下实现体都被证明未被触达——探针实现体
  抛出的 sentinel 绝不允许出现在失败文案里。
- 组合声明的装配校验测试带反证控制：同一份库去掉 contractVersion 仍然抛错，证明该 op 确实
  被校验器走到，而不是被跳过。
- 能力覆盖断言改为按两条轴的**并集**计数，而不是互斥集合相加，同时声明两者的条目只计一次。
- 被互斥逼出去的 `fuse` 依赖清单可以按能力映射表补回；本次改动刻意不补——逐名清单必须来自
  能力映射表，而不是凭记忆填写。
