# Agent Note: mesh 执行链冻结，BREP 是唯一受支持的执行链

Status: implemented

[English](2026-11-07-mesh-chain-frozen-brep-only.md) | 中文

## Problem

引擎在同一分派面后挂两条执行链：manifold-3d mesh 链与 OCCT/brepkit BREP 链。每个 dual-op 都带双实现，`auto` 模式在 BREP 链断链时静态降级到 mesh，且现行指令要求每个新 op 以 mesh 为默认路径提供支持。双实现的维护让每个能力的修复面与测试面翻倍，mesh 侧缺陷持续堆积（螺距硬编码、头高补偿错位），却没有任何消费方需求为这份维护成本背书。

用户指令（2026-11-07）：「最后我要强调一下，mesh链路给我忽略，未来不再维护，只支持brep。文档里写清楚。」

## Decision

**BREP 是唯一受支持与维护的执行链；mesh 执行链冻结。**

- 新 op、新能力、缺陷修复、新测试一律只落 BREP 实现。
- mesh 实现留在代码树中作为冻结遗留面：不新增能力、不修复缺陷（已知缺陷在发现处登记、不修）、不写新测试。既有 mesh 测试文件作为冻结基线保留，唯一要求是不红。
- 自此新增的键与参数在共享参数层解析，但支持与测试目标仅为 BREP 链；mesh 行为不定义、不承诺、绝不静默伪装。
- 链切换机制（auto 模式静态降级 mesh）在运行时仍然存在；切换后的 mesh 段运行的是冻结代码。新开发只以 BREP 为目标。
- mesh 作为数据表示是另一件事实，不受影响：`Shape` 仍是三角网格载荷，SDF 产物仍以 mesh 表示，显示三角化仍来自引擎对 BREP 模型的三角化。
- 根指令（`AGENTS.md`）写明 BREP-only 支持面；不再要求新 op 支持 mesh。

## Alternatives considered

**继续维护两条链。** 用户指令否决：mesh 侧没有任何为持续维护背书的需求，双链维护让每个能力的交付速度减半。

**直接删除 mesh 实现。** 否决：存量脚本、`mode:'mesh'` 宿主与 SDF 产物仍在其上执行；删除是一场无现实需要的破坏性清扫。冻结以零维护成本保住运行时行为。

**把 mesh 重新标注为预览路径。** 否决：按引擎定位，mesh 是正式数据（SDF 产物），不是预览；改标签会错误描述这条链的产出。

## Consequences

- mesh 侧登记的缺陷（custom pitch 硬编码、头高补偿错位）按设计保持未修：登记，不修。
- 既有 mesh 测试文件继续在 CI 里作为冻结基线运行：必须不红，但不写任何新 mesh 覆盖。
- `docs/api-contract.md` 仍把双链运行时（模式、`auto` 降级）描述为当前行为；冻结是叠加其上的维护立场，记录在本 Note 与根指令中。
- 下游消费方对 2026-11-07 之后新增的任何能力必须运行 BREP 链。
