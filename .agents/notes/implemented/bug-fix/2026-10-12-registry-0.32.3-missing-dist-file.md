# Agent Note: 0.32.3 registry dist shipped without solve-tree.js — publish manifest verification gap

Status: implemented

English | [中文](2026-10-12-registry-0.32.3-missing-dist-file.zh.md)

## Problem

`@faicad/faijs@0.32.3` was published with a **broken dist**: the registry tarball did
not contain `dist/api/assembly/solve-tree.js` (its `.d.ts` was present), so every
`import { solveAssemblyTree } from '@faicad/faijs/api/assembly/solve-tree'` in a
consumer resolved to a missing ESM file and crashed with
`ERR_MODULE_NOT_FOUND` at import time. The consumer (@faicad/faijs-cadquery parity
harness) could not run **any** assembly mirror through the published package; the
whole assembly domain only worked against a locally packed tarball.

Downstream evidence trail (2026-10-11/12, faijs-cadquery repo):

- `@faicad/faijs@0.32.3` from the registry: `dist/api/assembly/solve-tree.js` **absent**,
  while `solve-tree.d.ts` exists → tree-mode assembly solves (`CqAssembly.solve()` on
  nested members) unusable.
- Locally packed `faicad-faijs-0.32.3.tgz` from the same commit (`edc82fa9`, built with
  `npm run build -w @faicad/faijs` + `npm pack`): file **present**.
- `@faicad/faijs@0.32.4` and `0.33.2` from the registry: file **present**; verified by
  the consumer's full assembly suites (56/56 green).

So the defect was isolated to the 0.32.3 registry upload — the source tree was fine,
the local tarball was fine, only the published artifact was incomplete.

## Decision

The root cause classification is a **publish-manifest verification gap**: nothing in
the release flow checked that the uploaded tarball's file set actually matches the
workspace build. `files: ["dist", ...]` in package.json declares the intent, and the
local `npm pack` honored it, but the artifact that reached the registry did not match —
and no gate compared the two.

1. **Pre-publish checksum gate**: before `npm publish`, compare the tarball's file
   list against `npm pack --dry-run` of the freshly built workspace package (or a
   stored manifest of `dist/**`), and hard-fail on any missing `dist/**` file that
   the local build produces. Cheap (file-list diff), catches exactly this class.
2. **Post-publish smoke**: after upload, `npm install` the published version into a
   scratch dir and run one import of a deep subpath (`@faicad/faijs/api/assembly/solve-tree`)
   plus the CLI smoke (`faijs-cli.ts check` on a fixture). This is the belt to the
   checksum's braces: it validates the registry copy, not the local one.

Until the guard lands, the working rule for publishers is: never trust a local pack
as evidence that the registry copy is complete — verify the registry tarball directly
(`npm pack @faicad/faijs@<ver>` + file-list diff, or install-and-import smoke).

## Alternatives considered

- **Do nothing (0.32.4 already fixed it).** Rejected: nothing prevents recurrence;
  the failure mode is silent (consumers only find it at import time, and a consumer
  can waste a day attributing it to their own code — which is what happened here).
- **Blame the registry/CDN.** Rejected: no evidence of transport corruption; the
  likeliest cause is a publish run from a stale/partially built `dist/` or a pack
  from a different working state than the verified one. A checksum gate covers both
  hypotheses without needing to identify which one occurred.
- **Switch to a monolithic single-file dist.** Rejected: bundling `dist` into one
  file would mask the file-level verification gap rather than fix it, and changes
  the consumption surface for every subpath import.

## Consequences

- 0.32.3 is a broken release on the registry; consumers must pin `>=0.32.4`. Consider
  `npm deprecate @faicad/faijs@0.32.3` so tooling flags it.
- The release flow gains (with the guard change) a tarball-vs-workspace file-list
  check pre-publish and an install-and-import smoke post-publish; a mismatch fails
  the release instead of shipping a partial dist.
- Downstream (faijs-cadquery) recorded the incident and its verification trail in its
  parity plan; the misattribution cost (one A/B session wasted trying to diff against
  the broken registry package) is the concrete motivation for the post-publish smoke.

## Verification

- `@faicad/faijs@0.32.3` registry tarball: `dist/api/assembly/solve-tree.js` absent
  (reproduced by direct install on 2026-10-11).
- `@faicad/faijs@0.32.4` / `0.33.2` registry tarballs: file present; consumer assembly
  suites 56/56 green against both.
- Local pack from the 0.32.3 commit: file present — proving the defect is bounded to
  the registry upload, not the build.
