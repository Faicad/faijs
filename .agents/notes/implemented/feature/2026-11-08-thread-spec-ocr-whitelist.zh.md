# Agent Note: `parseThreadSpec` 的 OCR 变体白名单

Status: implemented

[English](2026-11-08-thread-spec-ocr-whitelist.md) | 中文

## Problem

描述性螺纹规格（`thread: 'M16-6H↧18'` / `spec: 'M16'`）越来越多地由读图纸标注的 OCR 管线喂入。真实 OCR 输出带着全角字符、错误的破折号/引号/箭头字形、欧式小数逗号、以及标注关键词 `THRU`/`DEEP`——严格文法全部拒绝。同时该串是攻击者可达的输入面：同形异码（西里尔 `М`）、零宽/双向控制字符、注入载荷、超长输入，永远不准被静默容忍或猜测成几何。

用户要求（2026-11-08）：容忍必须是**提前枚举的白名单**，不是开放式输入兼容；白名单外输入必须显式拒绝（`E_THREAD_SPEC`）；恶意与故意混淆输入（注入、同形异码、零宽/双向字符、超长 DoS）必须防御；方便性与安全性的界限必须明确且有测试。

## Decision

`parseThreadSpec` 经三层白名单规范化。规范化只把字符映射**进**既有文法字母表——绝不放宽文法——文法仅有的新增是枚举产生式：

- **L1 字符等价类**：NFKC（全角形、分数字形——`½` → `1⁄2`，U+2044 映射 `/`）、单字形近字映射（破折号变体 → `-`、`*`/`·`/`∗` → `×`、弯引号/撇号 → `"`——NFKC 拆开的 `″`→`′′` 对先坍缩成一个英寸符号、`⇩`/`⤓` → `↓`）、数字逗号小数（`1,5` → `1.5`）、前导点小数英寸（`.25"`）、OCR 边缘杂质剥离（只剥两端的杂散括号/引号/标点；前导 `.` 与尾部 `"` 有意义、永不剥离，破折号永不剥离——`-M16` 必须解析失败）。
- **L2 枚举关键词后缀**：`THRU`/`THROUGH` 置 `ResolvedThreadSpec.thru = true`（通孔；`depth` 保持 undefined ≡ `fai_drill` 既有通孔语义），`<depth> DEEP`（空格分隔的裸数字）置 `depth`。矛盾组合全部显式报错：THRU 与任何深度写法同给、↓ 后缀与 DEEP 同给。
- **L3 闭字母表公差修复**：公差等级 token 仅在**唯一候选**时修复（`GH` → `6H`、`ZB` → `2B`、`6N` → `6H`）；自由数字绝不猜测——报错信息附最近表项建议（OCR 加权 Levenshtein ≤ 2 编辑距离、混淆对半价、数字邻近度决胜使 `M17` 建议 `M16` 而非 `M12`），建议只出现在报错文本里，绝不自动应用。

**安全边界**（全部 `E_THREAD_SPEC` 拒绝）：超过 64 字符（正则 DoS 上限，NFKC 之前检查）；不可见/双向控制字符（U+200B–U+200F、U+202A–U+202E、U+2060–U+206F、U+FEFF，原文与 NFKC 后各查一遍）；规范化后的字母表守卫（`A-Z 0-9 - × ↓ / " . #`），按码点拒绝同形异码、注入载荷、标记语言、未知标点。

**TPI 防窃守卫（承重）**：imperial 分支只在 token 第二字符是字母时才做公差修复。没有它，`LETTER_LOOKALIKES['8'] = 'B'` 会把 TPI token `18` 修复成公差 `1B` 并静默丢掉 TPI；该守卫由 GOTCHA 回归测试钉死。

**`fai_drill` 互斥**：`thru`（来自 THRU）与显式 `depth` 参数同给 → `E_ARG`，并入既有串内-vs-参数互斥组。

**文档**：生成的 AI/用户手册（`ops-api-inventory.md`/`.zh.md`）经其 JSDoc 源在 `fai_drill` `thread` 与 `screw` `spec` 行记录白名单（`gen-ops-api-inventory` 再生）。

## Alternatives considered

**开放式输入兼容（一切看似合理的都规范化）。** 用户否决：只接受提前枚举的白名单；其余必须显式拒绝——既为安全，也因为错误猜测产出静默错误的几何。

**自动修复自由数字（`M1O` → `M10` 本体数字）。** 否决：本体直径/螺距是自由数字，近似候选众多；猜测有静默错几何风险。`M1O` 改为报错并附建议。

**把破折号当 OCR 边缘杂质剥离。** 否决：会让 `-M16`/`M16-` 解析成合法规格；畸形信号比除杂便利更有价值。

**让 `screw` 在其 `spec` 里拒绝 `THRU`/`DEEP` 后缀。** 本次未做：`screw` 本就忽略深度后缀（既有行为，螺纹系列才是它消费的唯一来源）；`thru` 同样忽略而非建模。登记为已知限制，不扩范围。

**规范化时静默容忍零宽字符。** 否决：不可见文本是攻击面，不是 OCR 输出；原文与 NFKC 后都检查、都拒绝。

## Consequences

- `parseThreadSpec` 接受同一批规格的 OCR 变体（解析器测试 85/85，含 56 个新 OCR 用例），既有 11 条坏输入全部保持报错。
- 白名单可枚举、单点文档化（`thread-spec.ts` 文件头 + GRAMMAR_HELP），边界由安全测试锁定：同形异码、零宽/双向、注入载荷、超长输入、未知关键词。
- 报错信息携带最近表项建议（`M17` → `M16`、`NPT1/2` → `PT1/2`），提升 AI/OCR 管线可恢复性，且绝不自动应用。
- `ResolvedThreadSpec` 新增可选 `thru` 字段；PMI 数据逐字段构建，下游形状零变化。`fai_drill` 对 THRU + 显式 `depth` 报 `E_ARG`。
- NFKC `″` → `′′` 拆分这一 Unicode 坑保留为回归测试（两个撇号是一个英寸符号，不是两个）。
- 仅 BREP 链；mesh 链冻结。
