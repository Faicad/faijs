# 拓扑命名与几何谓词：faijs 选边机制的能力边界分析

> 本文回答两个问题：① 传统 CAD 的拓扑命名与追踪（persistent naming / topology tracking）
> 解决的是哪一类问题；② faijs 若采用 CadQuery 的 `|Z` 这类运行期几何谓词选边，能否达到同样效果。
> 并给出「在什么约束下可以用、用到什么程度」的分级结论。
> 本文只做能力盘点与结论，不含实施步骤。

## 用户原始需求（原话）

1. 「给我解释一下，这些拓扑命名和追踪在传统cad里解决的是哪类问题。如果采用faijs建模，并采用cadquery这种"|Z”这种拓扑指定的方式，是否能完成同样的效果？」
2. 「如果我不改上游的代码，只改参数。CadQuery 的运行期几何谓词还会有你说的问题吗？比如你举的那个例子，是在上游添加了生成凸台的代码。**我完全可以禁止这个操作，要求新加的凸台写在代码的最后**」

## 结论摘要（TL;DR）

1. **拓扑命名解决的是"重放后同一个面/边是谁"**——参数化 CAD 改一个参数就重放整棵特征树，
   而倒角、抽壳、草图附着、装配 mate、工程图标注、CAM 走刀、仿真边界全都引用子形状。
   这是 CAD 领域几十年的老问题（persistent naming problem）。
2. **`|Z` 是运行期几何谓词，不是身份**：它每次执行重新求值，回答"现在哪些边符合条件"，
   而不回答"上次那条边现在是谁"。两者是不同层的东西，不是同一能力的两种实现。
3. **用户第 2 问的约束成立，且确实消灭了一整类故障。** 本文 §6.1 明确更正：
   笔者先前用"上游新增凸台"举的例子属于**改代码**，不属于改参数，在该约束下不会发生。
   更进一步，faijs 的 UI 交互模型（`part0 → part1 → … partN` 链式追加）天然满足"只能末尾追加"。
4. **但风险没有归零，而是从"结构漂移"转移到"参数漂移"，且集中在极值/排序/范围类谓词上**
   （`>Z`、`CenterNth`、`BoxSelector`）。方向类（`|Z`）在形状族稳定时是安全的。见 §7 分级表。
5. **存在反向情况：集合语义下谓词比身份更鲁棒**（§8）——"所有竖边都倒角"用 `|Z` 在边消失后
   继续工作，而显式引用会报 `E_TOPO_DELETED` 让模型断掉。
6. **建议从"限定符只作便利层"改为分级策略**（§9）：方向/类型类可作主机制，
   极值/排序/范围类必须固化为显式引用。

## 1. 拓扑命名与追踪解决什么问题

### 1.1 参数化 CAD 的模型不是几何，是一串特征

改任何一个参数 → 整棵特征树重放 → 几何重新生成。而大量特征必须引用子形状：

| 引用者 | 引用的东西 |
|---|---|
| 倒角 / 圆角 | 参与修饰的边 |
| 抽壳 / 拔模 | 移除面、中性面 |
| 草图 | 附着在哪个面上 |
| 装配 mate | 两个面贴合 / 同轴 |
| 工程图 | 尺寸基准边、剖切面 |
| CAM | 走刀面、避让面 |
| 仿真 | 边界条件施加面 |

重放后，面的数量、顺序、位置都可能变。核心问题一句话：

> **"我上次选的那条边，现在是哪个？"**

这就是 **persistent naming problem（拓扑命名问题 / 持久命名问题）**。它的用户可见形态每款
参数化 CAD 都有：SolidWorks 改个尺寸后圆角"跳"到别的边或报 dangling reference；
Fusion 360 回滚时间轴后下游特征错乱；Onshape 为此专门做 topology tracking。

### 1.2 为什么难：拓扑变化不是一对一的

| 变化 | 含义 |
|---|---|
| 1 → 1 | 面被修改但仍是单个面（如面上开了孔） |
| 1 → N | 面被切割成多片，一个身份对应多个后继 |
| N → 1 | 多个面合并成一个 |
| 消失 | 面/边被完全移除 |
| 新增 | 生成了没有前驱的新面（如圆角过渡面） |

faijs 的 `FaceEvolution`（`brep/face-evolution.ts:22-28`）记的就是前四种：
`输入面 ordinal → 输出面 ordinal[]`，"不在 map 中"表示未被修改或已删除。

### 1.3 各家怎么做

| 系统 | 做法 |
|---|---|
| Parasolid / Onshape | 内核持久 ID + 演化记录；Onshape 把大量版本门写进 `fillet.fs`（433 / 445 / 449 / 470 / 601 / 886 六处 `isAtVersionOrLater`），其中一半就是在修引用稳定性 |
| CATIA | "Keep / No keep" —— 让用户显式声明选择意图，把判定成本转给用户 |
| SolidWorks | 以 dangling reference 的形式把问题暴露给用户 |
| **faijs** | 同一件事的**文本化**实现：role 血缘（`origin` + `role`）+ 每次语句执行后的演化传播（`RoleTable`，`topology/naming/types.ts:114`） |

faijs 的额外优势：身份是**纯文本、JSON 安全、可手改、可 diff**——写进 `.fai.js` 的
`{origin:'box', role:'box:top'}` 人能读懂，这比二进制持久 ID 更适合 code-CAD。
代价：每条语句都必须做一次演化传播，基础设施不能断（断链的后果见 §3.2）。

## 2. CadQuery 的 `|Z` 是另一类东西

`|Z` 是**运行期几何谓词**：对当前几何做一次筛选（"方向平行于 Z 轴的边"），每次执行重新求值。
它不记录、不比较、不记得上次选了谁。

| 维度 | role 身份（faijs） | 几何谓词（CadQuery） |
|---|---|---|
| 语义 | "上次那条边" | "现在符合条件的边" |
| 求值时机 | 引用时解析，依赖演化传播 | 每次执行重新求值 |
| 可复现性 | 跨重放稳定 | 依赖当前几何 |
| 能否表达"其中一条" | 天然精确 | 只能表达"一类"，须堆叠谓词逼近 |
| 能否回显 | 能（回指同一个 role） | 不能（回显的是当前匹配集合） |
| 引用消失时 | 三态可判（`deleted`/`ambiguous`/`not-found`） | 只能判"空集"，判不出"少了一条" |
| 集合语义（"所有竖边"） | 要逐条枚举 | 天然合适 |

**关键差异：身份能表达"否定的事实"。** `TopoResolution` 是三态的
（`topology/naming/types.ts:119-130`）："这条边没了"是可判定、可报错的；
谓词区分不了"没有符合条件的边"和"我谓词写错了"，只能静默生产一个空集或错集。

## 3. faijs 侧的两条现状事实（影响成本与风险）

### 3.1 cq-compat 现有的选择器是"不支持就报错"，不是"猜"

`packages/cq-compat/src/workplane.ts:1514-1538`：

```ts
const m = /^\|([XYZ])$/.exec(sel.trim())
if (!m) throw new Error(`[cq-compat] unsupported edge selector "${sel}" (supported: |X |Y |Z)`)
```

- **只支持 `|X` / `|Y` / `|Z` 三种**，其余一律抛错——这是正确的 fail loud 姿态，值得沿用。
- 判定方式是**边包围盒三轴 extent 的相对比较**：轴向 extent 占优，且两个垂直方向 extent
  ≤ `PAD = 0.5` mm（`:1526`）。注释说明 PAD 是为了吃掉内核给边包围盒加的 ~0.1 mm 容差填充。
- **含义：该判定与模型尺度耦合。** 垂直方向 extent 超过 0.5 mm 的边不会被判为轴向平行，
  微小特征（边长 < 0.5 mm 量级）的判定行为不稳定。这是"认领这套方言"前必须知道的成本。
- 另：`fillet(wp, radius)` 在无选择器时作用于**全部边**（`:1593`），且失败会向上传播——
  `:1543-1547` 的注释记录了此前"静默返回未圆角形状"导致 mini_lathe 零件圆角整批消失的故障。
  **静默失败是这个领域最容易踩的坑**，任何降级路径都必须避免重蹈覆辙。

### 3.2 脚本参数形态上，字符串限定符没有语法障碍

旧 parser（实参类型白名单）已随 direct-executor 架构移除，`.fai.js` 源码直通 JS VM，
`{ edges: '|Z' }` 这类字符串字面量在脚本面不存在解析限制。

待确认：UI 通道的 `lang/expr-validate.ts` "editable whitelist"（`:103` 的 `E_VALUE` 分支）
是否接受字符串字面量——只影响 UI 里手改参数时的实时校验，不影响执行。

## 4. 风险重估：用户的约束成立，我此前的例子举错了

### 4.1 更正

约束 A：只改参数值，不改上游代码结构。
约束 B：新特征只能追加在末尾。

**在 A + B 下，"上游新增凸台导致 `|Z` 命中集合扩大"这类故障不会发生。** 笔者此前用它举例
是不匹配的——那是改代码，不是改参数。用户指出得对。

更进一步：**约束 B 在 faijs 里是天然成立的。** faijs 的 UI 交互模型是
`选中 part → 施加操作 → 生成 partN 变量`，语句只能追加在末尾，
"在圆角之前插入一个凸台"这种操作在编辑器里根本不会生成。

### 4.2 剩下的风险：参数漂移

约束消灭的是结构漂移，但**命中集合仍会随参数连续变化，并在某些参数值处跳变**，且跳变点取决于
几何、无法提前预测。分两类：

**(a) 极值 / 排序 / 范围类谓词——即使只改参数也会翻车**

两个凸台 A(h=10)、B(h=12)，`>Z` 选中 B 的顶边。把 h_A 从 10 改成 15（代码一行没改），
`>Z` 的目标整体换成 A。**不报错，模型照出，倒角倒在了另一个零件特征上。**

**(b) 方向类谓词——在形状族稳定时安全，但有前提**

`|Z` 对 box / 圆柱 / 圆锥这类 primitive 是稳定的（永远是同样的竖棱）。前提有三条：
1. 不因布尔切割改变边的数量（切割体尺寸改到"不再切穿"会改变边的集合）；
2. 没有角度参数跨越临界值（拉伸草图里一条线的角度从 90° 改到 85°，那条边不再 `|Z`，**静默少倒一条**）；
3. 圆角半径没有大到吃掉整个面。

### 4.3 与漂移无关的固有局限（约束解决不了）

1. **回显粒度**：用户点了 3 条边，UI 生成 `|Z`，下次打开高亮 4 条。这不是错误，是表达粒度问题——
   只要在 UI 上显示"当前匹配 N 条边"并要求确认，多数场景可接受。
2. **选不出"其中一条"**：`|Z` 只能给全集；想选 4 条中的第 2 条，必须回到显式引用。
3. **判不出"少了一条"**：命中集合从 4 变 3 时，谓词无从知道用户期望的是 4。

## 5. 谓词风险分级表

| 谓词类型 | 例子 | 只改参数时 | 判据 |
|---|---|---|---|
| 方向类 | `\|X` `\|Y` `\|Z` | **稳定**（形状族固定时） | 边方向一般不随尺寸变；见 §4.2(b) 三条前提 |
| 类型类 | `%Plane` | **稳定** | 面类型不随尺寸变 |
| 极值类 | `>Z` `<Y` `>X` | **脆** | 选的是"赢家"，赢家由参数决定 |
| 排序 / 索引类 | `CenterNth` `RadiusNth` | **脆** | 排序随尺寸重排 |
| 范围类 | `BoxSelector` | **脆** | 边移进 / 移出包围盒 |
| 组合类 | 交 / 并 / 差 | 取最脆的一项 | — |

## 6. 反向情况：集合语义下谓词比身份更鲁棒

这条容易被忽略，但它决定了两类机制各自的主场。

假设用户的心智是"**所有竖边都倒角**"：

- 用 `|Z`：改参数后某条竖边消失了 → 剩下 3 条继续倒角，模型照常产出。
- 用显式 `EdgeTopoRef`：那条边没了 → `E_TOPO_DELETED`，整条链断掉。

**集合语义天然属于谓词，"指名道姓"才需要身份。** 判据是用户意图：
- "这些边"（一类）→ 谓词更合适，身份反而过严；
- "这条边"（一个）→ 身份更合适，谓词表达不了。

## 7. 建议：从"限定符只作便利层"改为分级策略

前提：确认 faijs 的约束是 **只改参数 + 语句只能末尾追加**（后者由 `partN` 链式结构天然保证）。

1. **方向类 / 类型类限定符可作主机制**——尤其集合语义场景，且比显式引用更抗参数变化。
   UI 可直接生成 `edges: '|Z'`，并显示"当前匹配 N 条边"由用户确认。
2. **极值 / 排序 / 范围类必须固化为显式引用**——UI 生成时立刻把求值结果转成 `EdgeTopoRef[]`，
   不让脆谓词留在脚本里。这条不依赖"改代码"就能翻车，因此不可豁免。
3. **"选其中一条"只能显式引用**——谓词表达不了，与漂移无关。
4. **空集必须报错**——求值命中 0 条时抛"这条圆角没有匹配到任何边"。
   这能覆盖大部分失效（代价：判不出"少了半条"）。
5. **不支持的谓词一律报错，禁止静默降级为"全部边"**——沿用 cq-compat `workplane.ts:1519`
   已有的正确姿态，并引 `:1543-1547` 记录的静默失败故障为戒。
6. **共用一份实现**：core 出 `api/edge-selector.ts`，cq-compat 与 fillet / chamfer 都用它，
   避免第二份方言。

## 8. 待确认项

   若将来支持插入编辑，§4.1 的前提失效，方向类谓词需重新评估。
2. `PAD = 0.5` mm 是否改为按模型尺度自适应（cq-compat 现为硬编码常量）？
3. `lang/expr-validate.ts` 的 editable whitelist 是否接受字符串字面量（影响 UI 实时校验，不影响执行）？
4. 极值类谓词是否需要在 UI 上强制"固化"提示，还是仅在生成时自动固化、不打扰用户？
