# faijs 演进路线图（对标 Onshape FeatureScript）

> 日期：2026-08-16
> 定位：**语言级演进方向与顺序决策**。回答两个问题：① faijs 未来朝类 FeatureScript 的编译执行语言演进（分支/循环/子函数/外部库），如何在每个阶段保证方向不偏、顺序不乱；② 具体语法点（如参数顺序）未来是否强制，从而决定现在是否强制。

## 1. 终点形态（北向：v3+ 的 FeatureScript-like）

```
┌─────────────────────────────────────────────────────────────┐
│  .faijs 文本（JS 合法子集，acorn 可解析）                      │
│    import { chamfer } from 'faicad/std'   // 外部库           │
│    export function myFeature(cad, ctx) {  // 子函数/导出       │
│      for (const i of [1,2,3]) {           // 循环              │
│        if (i % 2 === 0) { … }             // 分支              │
│      }                                                        │
│    }                                                          │
└──────────────────────────────┬──────────────────────────────┘
                               ▼ 编译前端（语义分析/校验）
                      IR（作用域树 + 控制流图）
                               ▼ 编译后端
                  字节码 / WASM / JS（确定性执行）
```

**终点必须成立的性质（与当前红线同源，只强不弱）：**

| 性质 | 当前状态 | 终点状态 |
|------|----------|----------|
| 先静态校验后执行，绝不 eval | acorn parse → PartScript → replay | 编译前端（类型/形态/引用全量静态校验）→ 执行 |
| 禁止运行时回退（BREP 失败回 Mesh） | 静态规则判定（红线） | 编译期静态判定，运行时无回退概念 |
| 确定性执行（同输入同输出） | contentKey 度量 | 纯函数 + 确定性 IR |
| 平铺代码格式 | scriptToCode 输出 | 演进为**模块格式**（import + export function + 主函数）；**主函数体仍为平铺顺序（§0 不变量）** |

**关键资产：acorn 解析器路径保留。** 从"把 JS 文本还原成扁平语句序列"演进为"编译管线前端"，不换解析器、不换文本表示（JS 合法子集仍是序列化契约）。当前 `parseScript` 的 AST walk 就是编译前端的雏形。

## 2. 演进顺序（三个阶段，每阶段是上一阶段的严格超集）

### v1（现在）：扁平 DSL + 严格形态

- 形态：平铺语句序列，`const <id> = [await] cad.<op>(<inputVar>?, { args })`。
- **顶层顺序执行是永久形态（§0 不变量），不是过渡状态**：顶层永远没有控制流，对应 UI 用户操作的顺序语义。
- **本次审计的 L2 落地点**：parser 强制参数顺序、input 数量、split 解构形态（见 §4 判定表）。
- 执行：parse → PartScript（扁平 statements）→ replay（按 id 增量）。

### v2（下一步）：主函数容器正式化 + 子函数引入（控制流的唯一归属）

- **容器正式化**：`export default async (cad) => { … }` 从"自动包裹的隐藏形态"升级为**语言级主函数容器**（parser 已支持；codegen 仍输出平铺，两者经 parse/emit 互转）。
  - 平铺文本 = 主函数体的**简写**。**主函数体永远顺序执行（§0 不变量），永远不出现控制流**。
- **子函数引入**：控制流（`if` / `for` / `while` / 表达式赋值）**只允许出现在子函数内部**。`PartScript` 在顶层 statements 之外新增**函数节点**（函数名 + 局部作用域树）；顶层 statements 保持扁平，整体仍与文本双向同构。
- 执行：replay 对**顶层**保持按 id 增量（顶层永远是平铺段）；**函数调用是整体执行单元**——函数内部整体重放、不参与顶层每语句 diff 增量（增量边界显式化，写进契约，防止未来实现时破坏"禁止回退"红线）。
- 多返回值：`return { front, back }` / 解构消费 —— split 的多输出语法（解构）就是未来形态的预演，**现在强制 split 解构 = 提前对齐终点**。

### v3（远期）：子函数 + 外部库 + 编译

- 子函数：`function` / `export function`，参数**位置绑定**，具名 options 对象照旧；**函数体是控制流（分支/循环）的唯一合法位置**。
- 外部库：`import { … } from '…'`（acorn 顶层 ImportDeclaration 直接解析，基础设施已在）。
- 编译：AST → 语义分析（类型/形态/引用）→ IR（顶层顺序语句 + 函数级作用域树/CFG）→ 字节码 / WASM / JS。
- 增量执行退化为"编辑器便利层"而非语言语义；语言本身只保证确定性重放。顶层主函数体在编译产物中仍是顺序执行的入口。

## 3. 如何在"大方向上保证演进的顺序"（机制）

### 3.1 判定原则：每个语法决策对照终点做"兼容性检查"

对**每一个**语法点，先问：它在终点（编译执行语言）还成立吗？然后按三种结论行事：

| 判定 | 含义 | 现在的动作 |
|------|------|-----------|
| **终点强制** | 位置绑定、函数签名、多返回消费等语言基础 | **现在强制**（早强制省迁移，晚强制成破坏性变更） |
| **终点禁止** | 与编译/确定性/模块体系冲突（eval、动态 import、运行时回退） | 现在禁止，且**明确写进契约防止回潮** |
| **终点无关/不确定** | 命名风格、await 修饰、平铺 vs 容器 | 保持宽松或标记"待定"，**不提前锁死** |

**验证规则**：任何语法决策的文档提交必须附带一行"终点兼容性"说明（强制/禁止/待定 + 理由）。防漂移文档 `2026-08-16-syntax-change-anti-drift.md` 的三条防线（单一事实源 / 同步守卫测试 / CI）负责机械层面的漂移；本节负责**方向**层面的漂移。

### 3.2 参数顺序：未来必然强制 → 现在必须强制

**结论：强制，现在就要强制。**

理由链：

1. **位置绑定是编译语言的基础，无法靠类型推断**。v3 引入子函数后，`f(a, b)` 的参数按位置绑定；`cad.op(input, { args })` 中"哪个是几何输入、哪个是配置对象"由**位置**决定，不可能再按类型（Identifier→input / ObjectExpression→args）自动归类——用户自定义函数可以接受任意参数，类型推断法在子函数面前失效。
2. **现在宽容 = 为未来制造迁移债**。宽容解析意味着同一意图有两种合法文本（`op(input, {args})` 与 `op({args}, input)`）。v3 收紧为位置语义时，两类历史文本必须双写兼容或跑迁移工具。现在强制 → 文本唯一形态 → 未来零迁移。
3. **强制成本 ≈ 0**。codegen 已输出规范顺序（input 在前）；受影响的只有审计出的 20 处测试 fixture；AI/手写代码按文档生成即可。
4. **宽容的"收益"是虚假的**。宽容不是"方便 AI"，而是让 AI 学到错误模式（反序也被接受），并让"文本 ↔ codegen"往返产生 diff 噪音（codegen 归一化后与原文不同）。
5. **与 await 的对比**：`await` 是**修饰符**（省略不改变语义），可以宽松；参数顺序是**绑定语义**（颠倒就是另一个调用），必须强制。宽松与强制的分界是"是否改变语义结构"，不是"好不好写"。

### 3.3 其他语法点的判定（现行契约逐项）

| 语法点 | 终点判定 | 现在动作 | 说明 |
|--------|----------|----------|------|
| 参数顺序（input 在前、args 在后） | 强制 | **强制**（L2） | 见 §3.2 |
| input 数量（创建类 0、特征类 1、布尔 ≥2） | 强制（函数签名） | **强制**（L2） | 编译器就是签名校验器，现在是预演 |
| split 多输出解构 | 强制（返回对象 + 解构消费） | **强制**（L2） | `const part0_v1 = split(x)` 在终点是"绑定整个返回对象"，语义不同 → 现在就拒绝 |
| split/text 的静默降级 | 禁止（编译期就报） | **执行期显式报错**（L4） | 静默丢弃 back / 静默忽略多余 input = 编译语言不存在的状态 |
| `replay` 命名 | **禁止**（编译语言无"重放"概念） | **改名**：主执行入口 `execute`，增量更新 `update`（见 §3.6） | "重放"是 UI 录制心智模型残留，与"顶层顺序执行"不变量冲突 |
| 顶层控制流（if/for/while 直接写在顶层） | **禁止**（§0 不变量：顶层永远顺序执行） | **禁止**（parser 顶层拒绝控制流语句，ParseError） | 控制流只允许出现在函数内部 |
| `export default` 容器 | 强制（模块主函数） | 兼容支持，codegen 输出平铺 | v2 正式化为语言容器；**不**在 v1 拒绝旧格式，只修 fixtures |
| `return` 显式终端 | 强制（函数返回值） | 保留（parser 已支持，return 优先于自动推导） | 与终点同构，**不是**要废除的东西；审计 D 类修正的是"meta 进文本"，不是 return 本身 |
| id 命名（partN_vM） | 待定（任意标识符） | 宽松 | 不强制命名格式，避免提前锁死 |
| `await` 修饰 | 待定（async 语言） | 宽松 | 修饰符，语义不变 |
| 旧格式兼容 | 待定 | 保留 + 警告 | 给废弃窗口，见 §3.4 |

### 3.4 兼容窗口显式化

旧写法（如 args-first、旧 export-default 格式）设**废弃窗口**：

1. 新文本必须用新写法（parser 严格校验）；
2. 旧文本在窗口期内可解析（parser 兼容），但 `runtime.check()` 的 warnings 通道输出"已废弃写法"警告；
3. 窗口期满后移除兼容分支（迁移工具先行）。

窗口期长短是产品决策（D2），但"显式声明窗口"本身是机制要求——**不允许"永久无声明兼容"**，那是影子语法，会让文档契约与解析行为长期脱节（本次审计 D 类的根因之一）。

### 3.5 增量执行的边界声明（顶层永远增量，函数整体重放）

**顶层永远是平铺顺序段（§0 不变量）→ 永远按 id 增量**；控制流只存在于函数内部，函数调用是整体执行单元。此边界必须写进契约：

- 顶层每条语句参与"每语句 diff 增量"（id 身份契约覆盖全部顶层语句，**永久不变**——顶层永无控制流，不存在"平铺段"与"控制流段"之分）；
- 函数调用**整体重放**：函数内部不参与顶层 diff 增量；
- 函数重放失败 = 整体失败，**不存在**"保留前 k-1 条成功语句"的降级（与"禁止运行时回退"红线同构）。

### 3.6 命名决策：`replay` → `execute` / `update`（作用澄清）

**需求原始来源（用户原话）**：
> "还有replay这个名字就很有问题，它的作用是什么？"
> "增量更新叫 reconcile，这个有没有更简单的命名"

**决策记录（2026-08-16）**：增量更新命名经用户选择定为 **`update`**（候选：update/apply/sync/refresh/recompute；理由：6 字符够简、语义直接、CAD 惯例——Onshape 即用 update；且与 `execute` 形成清晰互补）。

**`replay` 的实际作用（`src/cad-runtime/runtime.ts` L145-244）**：给定一个 `PartScript`，按语句**顺序**逐条执行（`dispatchStatement`），维护 outputCache / BREP 链（含 mesh-only op 的静态断链判定），最后提取终端几何与终端 BREP solid。**它就是"执行脚本"——把建模定义顺序跑一遍产出几何**，与"重放录音"无关。

**命名问题的根源**：

1. **语义是"执行"，不是"重放"**：名字来自 UI 录制（`record*` → `replay`）心智模型的残留。但语言侧没有"录音"——顶层顺序执行对应用户顺序操作语义（§0 不变量），运行时就是把脚本跑一遍。
2. **一名字两义**：`replay` 同时承载两个不同概念——
   - (a) **全量确定性执行**一个 PartScript（`runtime.replay` / `replayScript`）→ 应叫 `execute`；
   - (b) **diff 后的增量更新**（宿主侧 `replayPart` / §4.3"重放规则"）→ 应叫 `update`（增量重算）。
   现在都用 replay，混淆了"执行"与"增量更新"两个阶段。
3. **与终点冲突**：编译执行语言没有"重放"概念（Onshape FeatureScript 是 evaluate/regenerate，即求值/重建模型）。名字提前对齐终点：**主入口叫执行（execute），增量更新叫 update**。

**改名建议（实施时执行，列入审计文档实施范围）**：

| 现状 | 改名 | 说明 |
|------|------|------|
| `CadRuntime.replay(script)` | `CadRuntime.execute(script)` | 主执行入口 |
| `replayScript`（test-helpers） | `executeScript` | 测试便利函数 |
| `ReplayOutput` | `ExecutionResult`（已存在，收敛） | api-contract §6.2 类型名 |
| `[ReplayValidator]` 错误前缀 | `[ExecutionValidator]` | ops 错误消息（波及 drill/extrude/engrave/split/knurl/transform/boolean/dispatcher） |
| `replayPart`（宿主侧增量） | `updatePart` | 增量更新，保留"增量"语义，区别于全量执行 |
| 文档"重放/replay"用语 | "执行（execute）/ 增量更新（update）" | syntax-design §4.3、api-contract §6 同步 |

> 注：改名涉及 src 多处与全部文档用语，属代码实施范畴；本文档先锁定决策，实施时按 L2/L4 同批或单独批次执行。

## 6. 一句话结论

> **参数顺序未来必然强制（位置绑定是编译语言的基础），所以现在必须强制——早强制只是修 20 处 fixture，晚强制就是一次破坏性语法迁移。** 大方向保证演进的机制是：每个语法决策对照终点做"强制/禁止/待定"三态判定并写进文档，机械层面用防漂移守卫（单一事实源 + 同步测试 + CI），方向层面用本节判定表。
